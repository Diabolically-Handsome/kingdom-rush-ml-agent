# elite-v3b「公平重测」方案（2026-10-12，待用户批准）

> 由主代理与一个只读的 Fable 5.1 子代理讨论三轮后综合而成。讨论期间没有运行任何游戏或 GPU 任务，也没有修改仓库里的任何代码。

## 1. 要回答的问题

用户怀疑：昨晚 8B/24B 表现差，原因可能在于提示词提供的局面信息不足。

核对提示词后确认，原简报只有关卡名和几条要点、生命、金币、波次、下一波旗帜预览（每条路的敌人数和 5 种特性标签）、场上敌人（按路线和进度四分段计数）、Boss 状态、英雄血量与是否在起点、法术是否就绪。缺少的有：

- 防御塔：类型、等级、位置、覆盖哪条路；
- 地图：路线走向、汇合点、出口；
- 局内历史：在哪丢了命；
- 敌人属性：飞行、护甲、魔抗、速度、皮厚等；
- P0 是和计划一起调好的这一事实；
- 推理机会：模型只能立刻回答一个字母。

另外，我生成的打法菜单有语义缺陷：

| 缺陷 | 数量 |
|---|---|
| 让援兵“阻挡”无法阻挡的敌人（985 个咨询点中出现在 314 个） | 469 个选项 |
| 为飞行或无法阻挡的敌人保留援兵 | 307 个选项 |
| 派近战英雄去拦飞行敌人 | 244 个选项 |
| 报警时把英雄派到已经走过去的敌人身后 | 214 个选项 |
| 第 17、26 关明明有多个出口，却从未提供“守出口” | — |

**本次只回答一个问题：同一模型、同一时刻，给足信息后，选择是否显著变好？** 至于“LLM 是否有超越简单规则的局面判断力”，在现有数据量下大概率测不出来（见第 3 节），只作探索性报告。

## 2. 讨论中确认的事实（Fable 用脚本和代码核实）

- **游戏已经导出了所需的大部分信息，只是简报没用上**，而且这些字段确实传到了 Python 端：
  - 防御塔的位置、射程、靠近哪条路；
  - 兵营士兵数和集结点；
  - 敌人的血量、护甲、魔抗、速度、飞行、无法阻挡；
  - 英雄等级；
  - 下一波每种敌人的属性。

  这些都在 Python 端计算，不改变游戏状态的导出，重放验证因此可以做到逐字节一致。路线几何没有现成接口，需要在开发副本里做一次只读探测（约 15 分钟）。
- **菜单缺陷对结果影响不大**：针对无法阻挡敌人的“拦截”打法，结果与普通拦截几乎相同（−0.029 对 −0.028）。修复是为了公平，单靠修复不会改变结论。
- **提升空间（天花板）**，用“选中打法减非 P0 打法平均”（d_np）衡量，均为两折交叉验证：

  | 做法 | d_np |
  |---|---|
  | 按关卡的固定打法排序 | +0.063 / +0.068 |
  | 按局面查表并向关卡排序收缩（最好的简单方法） | +0.081 / +0.073 |
  | 期望效应的理论上限 | 约 +0.09 到 +0.11 |

  零样本 8B 比固定排序低 0.094。所以把模型从“永远选 P1”拉回到固定排序水平，大约是 +0.07 到 +0.09，这是能测出来的。真正“按局面判断”能多出的部分只有约 +0.02 到 +0.04。
- **统计功效**（80% 功效下的最小可测效应，按 56 局原局聚类自助法）：

  | 对比 | 最小可测效应 |
  |---|---|
  | 同一模型，多信息对少信息 | 0.023–0.055（取决于有多少选择改变） |
  | LLM 对固定排序 | 约 0.063（要测出 +0.03 需约 250 局原局，约 13 小时分叉对局） |
  | LLM 对规则大脑 | 约 0.093 |

## 3. 设计（第一阶段，不新增分叉对局）

**数据**：现有 56 局稳守原局的 992 个咨询点和已测出的全部分支结果，全部是训练种子 1201–1204。评测种子和最终种子不动。

**多信息简报（最小可行集合，按预期作用排序）**：

1. **如实的打法说明**：写明执行器实际会做什么。例如“援兵会被投在它们脚下（飞行敌人挡不住）”“英雄走到 k 号路 35% 处”“守 k 号出口（没有已知威胁去那里）”。
2. **每条路按进度分段的防御覆盖**：哪些塔（类型、等级）覆盖哪一段，兵营士兵数和集结点。由塔的位置、射程和路线几何算出。
3. **中性的 P0 说明**：“P0 是战斗计划在搜索时一起调好的默认用法；其他打法偏离它。”不写任何“改动通常更差”之类的建议。
4. **卡片式敌人属性**：飞行、高护甲、高魔抗、速度快或慢、皮厚、护盾、召唤、下蛋、Boss。按游戏内卡片的说法分档，不给原始数值。
5. **每条路一行地图说明**：从哪进、从哪个出口离开、在哪汇合、是否有冰面。由探测结果自动生成。
6. **局内历史（总数）**：每条路至今丢了几条命、英雄阵亡次数。丢命只按“上一时刻”在场且到达 90% 以上进度的敌人归因，绝不用之后的信息。
7. **英雄等级。**

不放入：整局波次列表、精确计时器、精确血量、随机数等任何非人类信息（有单元测试检查）；也不放计划预告和逐波明细。

**作答方式（对照组）**：

| 组 | 说明 |
|---|---|
| 少信息新格式 | 原简报 + 打法编号 + 中性 P0 说明；另与旧格式结果比对，检查格式本身有没有影响 |
| 多信息 · 立即作答 | 8B 和 24B 都做 |
| 多信息 · 先推理再作答 | 主角为 24B，8B 视时间而定 |

推理组的做法：贪心生成一次推理，以模型自己写的“FINAL: [Pk]”作为它的选择；同时在推理之后按各种选项顺序给每个选项打概率，用于统计检验。另做两项诊断：在 100 个咨询点上反转选项顺序，看位置偏差；在 20 个咨询点上用单条生成复核批量生成的一致性。

所有组都用同一个独立离线打分脚本计算。它复制模型服务的加载和打分代码，不改动共享的模型服务。正式运行前先过一致性关：50 个咨询点上与昨晚的打分结果比对，选择 50/50 相同，概率差不超过 1e-3。

**参照（非 LLM）**：

- 交叉验证的固定排序；
- 按关卡排序；
- 同样信息下的规则大脑（rule_rich，阈值交叉验证得出）；
- 原规则大脑；
- 永远选 P1、永远选 P4、随机、稳守。

**预先登记的判定**（写入并冻结分析脚本之后才看任何 LLM 结果）：

- **第 1 层（信息有用）**：同一模型，多信息比少信息的 d_np 更高，配对区间不含 0。两个模型分别检验，做 Holm 校正。
- **第 2 层（追上简单方法）**：主角组的 d_np 大于 0（区间不含 0），且在两折中都至少达到固定排序的一半。
- **第 3 层（真正的局面判断，探索性，功效不足）**：两折都超过固定排序，且合并区间不含 0。
- **偏离率规则**：某组偏离少于 10% 时，只用“选中打法减 P0”评判。
- **控制**：对局进程（时钟）控制；“丢命历史”对照大脑，因为数据显示刚丢过命时偏离反而更差。

**停止规则**：

- 第 1 层或第 2 层没通过：结束“局中指挥官”这条路线，转向“LLM 做提案者、由搜索评测筛选”的设计。
- 两层都通过：可以进入第二阶段，需另行确认。

## 4. 第一阶段步骤与时间

| 步骤 | 内容 | 时间 |
|---|---|---|
| 0 | 写预先登记文本，冻结分析脚本（配对对比、rule_rich、丢命历史对照、分层判定、偏离率） | 1.5 小时 |
| 1 | 在任何游戏任务之前，先在 5090 上启动 GPU。写独立打分脚本并通过一致性关；跑少信息新格式的两组 | 2 小时 |
| 2 | 路线几何探测（开发副本，端口 9950 起，静音）；核查第 17、26 关的出口 | 1 小时 |
| 3 | 实现多信息简报、如实的打法说明、咨询时刻的状态记录、防泄漏测试；旧简报文字保持逐字节不变 | 4–4.5 小时 |
| 4 | 重放 56 局原局并记录状态；必须轨迹哈希一致，992/992 旧提示词哈希一致 | 0.5 小时 |
| 5 | 多信息立即作答两组 | 约 1 小时 GPU |
| 6 | 推理试跑 20 个咨询点（测速度和一致性），然后 24B 先推理组，8B 视时间而定 | 1–2.5 小时 GPU |
| 7 | 可选：用户亲自回答约 20 个简报 | 用户约 20–30 分钟，与其他步骤并行 |
| 8 | 按冻结的脚本分析并写报告，按层级和停止规则下结论 | 2–3 小时 |

合计约 12–14 小时工作，跨约 1.5 天，GPU 部分可以放在晚上跑。

## 5. 第二阶段（有条件，需另行确认）

- 修正打法的实际行为：不对飞行或无法阻挡的敌人用援兵；近战英雄不去拦飞行敌人；报警时的“拦截”改为去出口一侧；第 17、26 关提供“守出口”。需补跑约 900–1,400 局分叉，约 1–1.5 小时。
- 若想检验第 3 层，需要再加 90–250 局原局（新的训练种子），约 4.6–12.8 小时分叉对局。
- 只有在单步“选中打法减 P0”两折都为正时，才做整局实测：420 对，约 3–4 小时，LLM 推理期间游戏暂停（已声明的偏离）。

## 6. 规则（不变）

- 游戏全程静音；不改 Steam 游戏文件；不碰 RTX 5080 和另一个训练项目。
- 同一时间只跑一个游戏任务；探测端口 9950 起；GPU 服务必须在游戏任务之前启动。
- 评测和最终种子不用于训练或挑选；不对外发送、不推送。
- 人类能用的信息和操作才用，不多也不少。

## 7. 讨论中的主要风险

- **最大风险在解读，而不在工程。** 最可能的结果是“补足信息后，模型不再选荒谬的打法，追上固定排序，但看不出真正的局面判断”。这很容易被过度解读成“LLM 有判断力了”或“LLM 没用”。预先登记的层级、事先指定的主角组和天花板估计，就是为了防止这一点。
- **次要风险**：即使用中性说明，24B 也可能几乎总选 P0。那时只能用功效很低的“选中打法减 P0”来评判它。
